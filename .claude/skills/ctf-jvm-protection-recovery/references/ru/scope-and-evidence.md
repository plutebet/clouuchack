# Область задачи, доказательства и контрольные этапы

## Авторизация

Перед технической работой запиши: название CTF/лаборатории, цель, файлы и процессы в области задачи, разрешённые изменения и прямые запреты. Разрешение решать CTF не означает разрешения атаковать инфраструктуру организаторов, использовать найденные аккаунты или публиковать посторонние секреты.

Если процесс должен оставаться замороженным, зафиксируй PID и запрещённые операции. Перечисление процессов не разрешает открывать handle к отмеченному процессу, возобновлять или завершать его.

## Реестр доказательств

Для каждого исходного артефакта запиши:

- абсолютный путь и стабильное логическое имя;
- размер и SHA-256;
- источник по описанию пользователя;
- доверенный, недоверенный или сгенерированный статус;
- запрещено ли исполнение/загрузка;
- формат и архитектуру, определённые по содержимому.

Оригиналы держи read-only. Не перезаписывай единственный дамп или JAR. Каждый переход должен быть явным:

```text
original.jar -> semantic-decoded.jar -> native-restored.jar
             -> safety-patched.jar -> verified-release.jar
```

Для каждого этапа нужны input/output SHA, версия инструмента, перечень преобразований и результат проверки.

## Первичная инвентаризация

### Архив

Проверь ZIP/JAR, дубликаты entries, порядок и методы сжатия, manifest, Fabric metadata, mixin-конфиги, access widener, service descriptors, обычные `CAFEBABE` и непрозрачные записи, распределение размеров/энтропии, assets и native-ресурсы. После перепаковки подписи JAR становятся недействительными.

Имя из 32 hex-символов само по себе не доказывает, что это зашифрованный класс. Нужна корреляция количества, размеров, runtime-имён и поведения парсера.

### Дамп

Запиши тип/flags дампа, покрытие memory ranges, список модулей, thread contexts, exception stream и наличие private executable pages. Working set процесса и размер дампа не обязаны совпадать: влияют shared/mapped/guard/zero/uncommitted/excluded страницы и формат дампа.

Если антидамп заставляет файл расти бесконечно, используй region-aware сборщик: один snapshot карты памяти, только committed readable ranges, лимиты размеров, фиксация allocation base/protection/type и partial reads. Не размораживай защищённый процесс ради стандартного minidump.

### Native-образы

Определи точный build JVM, timestamp PE, image size, sections, imports/exports и состояние relocations. Образ из памяти отличается от дискового PE: headers могут быть изменены, relocations применены, часть секций отсутствует.

## Контрольные ворота

### A. Надёжное чтение памяти

- VA правильно переводится в диапазон/offset дампа;
- чтение работает через границы соседних ranges;
- module base и PE sections согласованы;
- проверяются canonical pointers и permissions.

### B. Надёжный поиск классов

- inferred layout подтверждён на известных JDK/game-классах;
- target-классы проходят проверку имени, super, CP и methods;
- измерен процент false positives.

### C. Пилотная сериализация

- JVM classfile parser принимает результат;
- internal name совпадает с путём;
- CP references валидны;
- bytecode дизассемблируется и проходит verifier;
- нужные framework-атрибуты сохранены.

### D. Самостоятельный декодер

- свежий результат строится только из original archive;
- покрыты все защищённые entries;
- dump/старый JAR не поставляют class bytes;
- fingerprints совпадают с dump-oracle там, где сравнение возможно.

### E. Запускаемый релиз

- все concrete methods проходят data-flow verification;
- class loading и mixins завершаются в чистой папке;
- все native roots реконструированы, безопасно заглушены или явно unresolved;
- опасные side effects проверены;
- assets, metadata, libraries и natives включены или документированы.

## Статус

Не придумывай проценты. Сообщай измеряемые числа: сколько protected entries найдено/декодировано, сколько классов сериализовано, concrete methods проверено, native roots классифицировано и сколько точных ошибок осталось. ETA давай только после замера скорости на репрезентативной партии.
