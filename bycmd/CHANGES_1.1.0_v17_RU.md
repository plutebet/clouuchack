# bycmd — Standoff 2 1.1.0, профиль v17

## v17.9 — тип оружия по dump.cs

- Цепочка из dump.cs: `uyg+0x30` — inline `WeaponContext` (там `+0x00 Owner`,
  что и было «номером экземпляра», `+0x10 Team`), `+0x50 ActiveWeapon : jrx`
  ⇒ `uyg+0x80`; `jrx+0x10` — `WeaponId.Raw` (байт). В `WeaponMetaData` имени
  нет (только скин/брелок/наклейки).
- Значения констант `WeaponIds` (G22, USP, AKR …) задаются в `.cctor`
  (RVA 0x9CADAE0) и в дампе отсутствуют, поэтому читаются из игры: по
  ADRP/ADD/LDR в прологе `.cctor` находится слот класса, класс проверяется
  по имени `WeaponIds` (`Il2CppClass+0x10`), статические поля
  (`Il2CppClass+0xB8`) дают байт на константу в порядке объявления.
  Проверка: встроенные значения попарно различны и не нули. Таблица пишется
  в лог одной строкой `WeaponIds table ready`.
- Иконка масштабируется по ширине бокса и не выходит за его границы;
  базовый размер уменьшен (16–34 px). Сканер имён v17.8 удалён.

## v17.8 — тип оружия по имени нативного объекта

- По логу c10d758 `uyg+0x30` оказался номером экземпляра оружия (4,5,7,9,
  11,13,15,17,18 по ходу матча, у одного врага 4 → 13), а не типом. Теперь
  он только детектор смены оружия.
- Тип определяется по имени: объекты, на которые ссылается `uyg` (глубина 2),
  считаются обёртками UnityEngine.Object, их нативный объект (0x100 байт)
  сканируется на ASCII-имена (внутри и по указателям), первое совпадение с
  таблицей имён даёт глиф. Переоценка только при смене номера экземпляра и
  раз в 3 с, пока тип не найден; лимит 500 чтений. Номера `#N` с экрана
  убраны; без найденного типа иконка не рисуется.
- Для локального игрока при неудаче в лог идут найденные имена
  (`[WEAPON] LOCAL inst=N no weapon name found; seen: ...`), в меню строка
  `my weapon: <имя>` либо `? (inst N)`.

## v17.7 — id оружия из uyg+0x30, убран сканер строк

  в лог при смене (`[WEAPON] local weapon id=N`) и показан внизу меню

## v17.3 — антикраш

Три слоя:

1. **Supervisor** (`main.cpp`, по умолчанию включён). Родительский процесс
   форкает overlay и следит за ним:
   - падение по сигналу → перезапуск через 1 с;
   - потеря EGL-поверхности (120 подряд неудачных `eglSwapBuffers`,
     код 3) → перезапуск через 0.5 с;
   - ошибка инициализации (дисплей/GUI, код 4) → до 10 повторов через 3 с;
   - зависание: heartbeat из главного цикла; нет сигнала 30 с вне
     `eglSwapBuffers` → `SIGKILL` и перезапуск. Блокировка внутри
     `eglSwapBuffers` (экран выключен) зависанием не считается;
   - защита от крэш-лупа: больше 8 перезапусков за 2 минуты → стоп;
   - чистый выход (кнопка Exit, SIGTERM) и «уже запущен» (код 2) —
     supervisor завершается. Флаг `--no-supervisor` для отладки.
2. **Crash-handler** (`src/other/crash.hpp`). На SIGSEGV/SIGBUS/SIGFPE/
   SIGILL/SIGABRT/SIGTRAP пишет в `bycmd.log`, `bycmd-crash.log` и logcat:
   сигнал, адрес ошибки, PC/LR/SP, PC и LR как смещение в `eeeww`,
   номер кадра, этап (`stage=esp-poses`, `render`, `menu` …), стек.
   Символы: artifact `eeeww-arm64-unstripped` в Actions,
   `llvm-symbolizer --obj=eeeww 0x<смещение>`. В сборку зашит git sha
   (`build=` в логе), чтобы смещения сверялись с нужным бинарником.
3. **Известные точки падения:**
   - Exit из меню вызывал `exit(0)` прямо из кадра при живых потоках
     тача и ImGui — теперь флаг и штатный shutdown, выход через `_exit`
     без статических деструкторов;
   - `eglSwapBuffers` без проверки результата: потерянная поверхность
     рисовалась «в пустоту» вечно — теперь счётчик и перезапуск;
   - ImGui-assert в release был отключён `NDEBUG` (молчаливое UB) —
     теперь пишется в лог (с ограничением частоты), выполнение продолжается;
   - `localtime()` без проверки на null.

Лог теперь не обрезается при перезапуске: родитель очищает файл один
раз при старте, дети дописывают.

## v17.2 — плавность и нагрузка

Плавность:
- Интерполяция позиций врагов (`visuals.cpp`, `motion_*`): хранятся два
  последних разных сэмпла, рисуется позиция на один интервал обновления
  игры назад, между ними линейно. Overlay на 120/144 Гц больше не
  показывает «ступеньки», когда игра идёт на 60/90 fps. Задержка —
  один кадр игры (~4 см на бегу). Переключатель в меню: `Smooth motion`.
- Проверка «одного кадра»: камера читается до и после поз игроков; если
  матрица изменилась — позы перечитываются. Бокс и камера всегда из
  одного кадра игры (иначе при быстрых поворотах дрожание в 1 кадр).
- Темп кадров: период дисплея = медиана 32 интервалов `eglSwapBuffers`,
  запас под vsync подстраивается по доле пропусков (`[PACE]` в логе раз
  в 10 с). Чтение памяти — в самом конце периода, перед рендером.

Нагрузка на игру:
- Поверхность overlay теперь `max × min` (например 2720×1224), а не
  квадрат `max × max`: вдвое меньше пикселей на clear/blend в GPU и
  на композицию в SurfaceFlinger каждый кадр.
- Чтений памяти на кадр примерно втрое меньше: объект игрока — один
  блок 0x98 (id, world, флаги, mtc, ydm, vqn, team); цепочка
  mtc → Transform → m_CachedPtr → {data, index, entries, parents}
  кэшируется на 500 мс, в кадре читаются только записи иерархии;
  флаг локального игрока берётся из блока, а не 3×N чтений; валидация
  реестра 4 раза в секунду, кэша игроков — 2 раза; никнейм — не чаще
  раза в 100 мс.
- Поток сканера: `nice 19`; проходы только пока не хватает реестра или
  камеры; в матче без результата — бэкофф 15 → 30 → 60 → 120 с.

  нет, обновление по тику симуляции. Это и есть «30 fps при движении»,

  неинициализированными, не сравниваются с заголовками объектов;

- `visuals.cpp`: гистерезис выбора fallback-камеры +40 (раньше +5, источники

## Камера: откуда теперь берутся матрицы

Старый код искал камеру эвристиками (декод `Camera.get_main`, обход графа,
имена классов) и чаще всего жил на синтетической камере из `yjp`/`vqn` с
FOV 60. Отдача и поворот в такой камере не совпадают с рендером — отсюда
«боксы уезжают вверх при стрельбе» и отставание при вращении.

Новая цепочка (`src/game/camera.hpp`):

```
локальный odq -> cpa(+0x20) -> pjy[] -> chc -> PlayerAnimationData(+0xA0)
    +0x100 bor MainCamera, +0x90 bor ArmsCamera
kmc / wot (найдены фоновым сканером по klass) : +0x10 bor, +0x20 Camera
    контроллер, у которого +0x10 == MainCamera  ->  Camera -> m_CachedPtr
    -> нативная Camera -> view/projection (+0x70/+0xB0, pattern-проверка)
```

Это матрицы, которыми GPU рисовал кадр: отдача, присед, FOV прицела —
всё внутри. Приоритет источников: `main-native` → `kmc-native` →
`main-bor` (синтетика из MainCamera ValueTransform) → `vqn-bor` →
`ios-transform` → `heap-camera`. Текущий источник виден в меню
(Settings → строка `camera:`) и в логе `[CAMERA] selected=... kind=...`.

Гипотезы, которые подтвердит только лог:
- `kmc` = мировая камера, `wot` = камера рук (по интерфейсам `etx`/`nri`
  и использованию в `npr`/`lcj`). Если наоборот — код всё равно выбирает
  контроллер по совпадению `bor` с `MainCamera`, а не по классу.
- `bor+0x48` или `+0x4C` — FOV (константа `zolb = 60` в том же классе).

## Лаг при вращении

- Сканы кучи (реестр, kmc/wot, PlayerAnimationData, Camera) вынесены в
  фоновый поток `scanner`. Поток рендера только валидирует адреса.
- Чтения на кадр сокращены: объект NetObject — одно чтение 0x48 байт,
  HP/maxHP — одно чтение, пара Transform — одно чтение, матрицы камеры —
  два чтения по залоченным оффсетам.
- Поза и HP читаются один раз, после камеры (раньше — дважды, до и после
  медленного поиска камеры).
- `game::valid()` больше не сканирует `/proc` каждые 60 кадров;
  живость — `kill(pid, 0)`.
- Late latch в `main.cpp`: после `eglSwapBuffers` цикл спит почти весь
  период кадра и читает память игры прямо перед рендером. Возраст данных
  на момент композиции — единицы мс вместо целого кадра.

## Запуск на других устройствах

Что сделано:
- 16 KB page size: `APP_SUPPORT_FLEXIBLE_PAGE_SIZES := true` +
  `-Wl,-z,max-page-size=16384`. Старый `eeeww` выровнен на 4 KB и на ядре
  с 16 KB страницами не запускается вообще.
- Лок-файл больше не фатален: пробует `/data/local/tmp/bycmd.lock`,
  `./bycmd.lock`, иначе работает без лока. Старая версия молча выходила с
  кодом 2, если `/data/local/tmp` недоступен.
- Лог-файл `/data/local/tmp/bycmd.log` (или `./bycmd.log`), в начале —
  модель, Android, page size, uid.
- `--diag`: проверяет дисплей, overlay+EGL+ImGui, `/dev/input`, pid игры,
  `libunity`, build-id и выходит. Это то, что нужно запустить другу на
  Xiaomi Pad 7 и прислать `bycmd.log`.
- Выход по SIGINT/SIGTERM с корректным shutdown.

Что **не** трогал: `ANativeWindowCreator.h` и `draw.cpp` (создание
overlay/EGL) оставлены как в исходнике. Если `--diag` покажет
`display info unavailable` или `initGUI_draw failed`, проблема в этом
слое на конкретной прошивке, и её надо смотреть по логу.

## Проверка сборки (fail closed)

`game::verify_build()` читает `NT_GNU_BUILD_ID` из замапленного
`libunity.so` и сравнивает с `v100::libunity_build_id = 69815f2befe135c2`
(из `remap_final`, самой библиотекой не перепроверено). При несовпадении
ESP не запускается, в меню `build: MISMATCH`, в логе ожидаемый и реальный
id. Если note не читается — вторичная проверка: имя класса в
`Camera_TypeInfo` должно быть `Camera`. `--skip-build-check` только для
диагностики.

## Прочее

- HP-бар считает процент от `max_hp`, а не от 100.
- Кэши `name/dead/hp` чистятся по списку живых объектов (раньше росли
  между матчами и могли скрыть живого игрока по старому «dead» адресу).
- Удалён мёртвый код: `is_scoping`, `deep_transform_diagnostics`,
  `scan_player_heap`, `alive`, декод `Camera.get_main`, цепочка по
  именам классов.
- Резолв ника остался эвристикой и подписан как эвристика.

## Сборка и запуск

```
cd bycmd/jni && ndk-build -j4      # NDK r27+ (флаги 16 KB)
adb push ../libs/arm64-v8a/eeeww /data/local/tmp/bycmd
adb shell "su -c 'chmod 755 /data/local/tmp/bycmd && /data/local/tmp/bycmd --diag'"
adb shell "su -c 'cat /data/local/tmp/bycmd.log'"
adb shell "su -c '/data/local/tmp/bycmd'"          # обычный запуск
adb logcat -s bycmd                                   # дублируется в logcat
```

Ключевые строки лога:

```
[INFO] device model=... android=... pagesize=...
[INFO] libunity build-id=... expected=69815f2befe135c2 match=1
[SCAN] pass 1 done: ... controllers=N animation=M
[CAMERA] chain local=... mainBor=0x... armsBor=0x...
[CAMERA] controller locked ... kind=main-native view=+0x70 proj=+0xB0
[CAMERA] selected=... kind=main-native
```

Если `kind` не `main-native` — прислать блок `[CAMERA]` целиком: там
видно, какие контроллеры нашлись и с какими `bor`.
